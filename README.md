## How to Run Each Module

### Module 1 — Data Pipeline

```bash
cd data_pipeline
python pipeline.py
```

This will:
1. Scrape ≥60 books from `books.toscrape.com` (first 5 all-products pages)
2. Clean the data (price → float, star rating → int, availability → bool)
3. Convert price_gbp → price_inr at **1 GBP = 105.50 INR** (fixed project constant)
4. Load into `books.db` SQLite with a normalized 2-table schema
5. Execute 6 SQL queries covering SELECT/WHERE, ORDER BY, LIMIT, DISTINCT, IN, BETWEEN, and JOIN
6. Demonstrate `pd.read_sql` vs `pd.merge` equivalence

**Fixed currency rate**: `1 GBP = 105.50 INR` — this is an artificial, project-defined constant with no date reference and requires no API.

## Design Decisions

### Module 1 — Data Pipeline

**Scraping scope**: Scraped the first 5 paginated pages of the "All products" catalogue, following each book's detail page for the category breadcrumb. This yields ≥60 books across ≥3 categories without cherry-picking categories manually.

**Missing value / parse failure handling**:
- `price_gbp`: uses pandas `to_numeric(errors='coerce')` to catch unexpected formats. Missing values are imputed with the median — chosen because the price distribution is right-skewed and the median is more robust than the mean to extreme values.
- `rating`: rows with unmapped text (not "One"…"Five") are dropped, because there is no sensible numeric default and these represent data-quality failures worth flagging rather than silently imputing.

**Currency conversion**: `price_inr = price_gbp × 105.50`. This fixed project-defined rate requires no external API, no network call, and no date reference.

**SQLite schema**: Two tables with a PK/FK relationship:
```sql
categories(category_id INTEGER PRIMARY KEY, category_name TEXT UNIQUE)
books(book_id INTEGER PRIMARY KEY, title, price_gbp, price_inr, rating, in_stock, category_id → categories)
```

---

### Module 2 — Analytics Pipeline

**Dataset loading**: Titanic is loaded **once** via `sns.load_dataset('titanic')` in `01_eda.ipynb` and immediately saved as `titanic.csv`. The modeling notebook (`02_modeling.ipynb`) reads only from `titanic.csv` — no second `sns.load_dataset()` call.

**Missing value strategy** (threshold rule: <5% → drop rows; 5–30% → impute; >30% → drop column):
| Column | Missing % | Strategy |
|--------|-----------|----------|
| `deck` | ~77.1% | Drop column — too sparse to impute; proxied by `pclass` |
| `age` | ~19.9% | Impute with median — robust to right-skewed age distribution |
| `embarked` | ~0.2% | Drop those 2 rows — under 5% threshold |

**Preprocessing pipeline**: `ColumnTransformer` wrapping per-column `Pipeline(imputer → scaler/encoder)` is fitted **only on the training split** and applied in transform-only mode to the test split. This is enforced structurally by the scikit-learn API.

**Stratification**: The dataset has ~38% survival rate (class imbalance). Stratified splitting ensures both train/test sets maintain this ratio, preventing biased evaluation.

**Imbalance conclusion**: All three strategies (baseline, `class_weight='balanced'`, SMOTE on train-only) performed similarly due to moderate imbalance. `class_weight='balanced'` is recommended for production as it requires no data resampling.

**Saved artifact**: `titanic_pipeline.joblib` contains the full `Pipeline(preprocessor → RandomForestClassifier)` — usable end-to-end on raw unpreprocessed input.

---

### Module 3 — Support Assistant

**MOCK_LLM toggle**: `MOCK_LLM=1` (default/unset) is the graded baseline — fully deterministic, no API key needed. `MOCK_LLM=0` enables optional Groq real-LLM path.

**Chunking**: Per-document chunking (each of the 8 policy docs = 1 chunk, since each is ~200–400 chars). Documents are short enough that sub-document chunking would create fragments too small for useful retrieval.

**Embeddings**: `all-MiniLM-L6-v2` via `sentence-transformers` — runs locally, no API key, no cost. Vectors stored in ChromaDB with cosine similarity metric.

**LangGraph graph**: 3 nodes (`classify_intent` → conditional edge → `retrieve_and_answer` OR `direct_answer`) using a `TypedDict` state. The routing logic is deterministic in both modes; only the answer-generation step branches on `MOCK_LLM`.

**Pydantic schema**: `ZeptoResponse(answer: str, sources: list[str], confidence: float)` — populated deterministically in mock mode (sources = retrieved chunk IDs, confidence = 1.0).
